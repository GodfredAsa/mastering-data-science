# Part 1: Concepts and principles

## 1.1 The workflow

Most of a project's value comes from framing and data preparation, not from the algorithm. A realistic split is 70-80% of the effort on understanding, cleaning and shaping data.

1. Define the problem and success criteria
2. Explore the data (EDA)
3. Clean and wrangle
4. Engineer features
5. Split the data and set up honest validation
6. Train a baseline, then better models
7. Evaluate, tune, interpret
8. Deploy, monitor, maintain

It is a loop: evaluation results often send you back to steps 2-4.

**Two task types** (both *supervised learning*, where each row has a known answer, the *target*, to learn from):

| | Predictive (regression) | Classification |
|---|---|---|
| Output | A number | A category or probability |
| Examples | House price, next month's sales | Will the customer churn? Is this spam? |
| Typical metrics | MAE, RMSE, R² | Precision, recall, F1, ROC-AUC, PR-AUC |

## 1.2 Framing the problem

Ask before coding:

- **What decision will the prediction support?** A churn score only matters if someone acts on it.
- **What exactly is the target?** "Churned" needs a precise definition.
- **What does each type of error cost?** Missing a churner and wrongly offering a discount have different costs. This chooses your metric.
- **What will be known at prediction time?** Anything learned only after the outcome cannot be a feature (*leakage*).
- **What is the baseline?** The current process, or predicting the average or most common class. A model that cannot beat it has no value.

## 1.3 Exploratory data analysis (EDA)

EDA builds intuition before modelling. Check shape, data types, summary statistics, missing values, duplicates and impossible values. Plot each variable alone (histograms, box plots, bar charts) to spot skew, long tails and suspicious spikes such as 0 or 9999 used as placeholders. Then look at feature vs target and feature vs feature. In classification, check class balance. Correlation is not causation: models find patterns that predict, not patterns that cause.

## 1.4 Data cleaning and wrangling

*Cleaning* fixes what is wrong. *Wrangling* reshapes data into one row per observation, one column per variable. The principle is **garbage in, garbage out**.

A key distinction used throughout Part 2:

- **Rule-based cleaning** (drop duplicates, fix typos, mark impossible values) uses no statistics learned from data, so it is safe to do **before** splitting.
- **Learned preprocessing** (imputation values, scaling, outlier caps, encodings) computes statistics from data, so it must be **fitted on training data only** and applied to validation and test data. Otherwise test-set information leaks into training.

| Issue | Typical treatment | Why |
|---|---|---|
| Duplicates | Drop exact duplicates, investigate near-duplicates | Copies landing in both train and test inflate scores |
| Inconsistent labels (`"Accra"`, `"accra "`) | Standardise case and whitespace | Otherwise one category fragments into several |
| Wrong types, mixed units | Convert and standardise | Silent errors, e.g. kg mixed with lb |
| Impossible values (age 150) | Mark as missing | They are errors, not information |
| Placeholders (9999, -1) | Mark as missing | They distort scaling and averages |
| Missing values | Impute, drop, or flag (see below) | Most models cannot accept blanks |

**Missing values: ask why first.** *MCAR* (random), *MAR* (depends on other observed variables, e.g. older customers skip the income question) and *MNAR* (depends on the missing value itself, e.g. high earners refuse to report). Common fixes: median for skewed numbers, most frequent value for categories, model-based imputation, and a **missing-indicator column**, because the fact that a value is missing is often itself informative.

## 1.5 Outliers

Decide what an outlier *is* before deciding what to do:

- **An error** (height 17 m, sqft typed with an extra zero): fix or set to missing.
- **Genuine but extreme** (a very wealthy customer): usually keep the information, but limit its leverage with a transformation (log), capping (*winsorising*, clipping at e.g. the 1st and 99th percentiles) or a model that is robust to it.

Never delete extreme values just because they hurt the fit; they may be exactly the cases you need to predict. Section [Outlier treatment: a decision guide](#outlier-treatment-a-decision-guide) summarises the options.

## 1.6 Feature engineering

Features are the information you give the model, and good ones often beat a better algorithm.

- **Encode categories**: one-hot for nominal, ordinal integers only when a true order exists, group rare levels.
- **Scale numbers** (standardise) for distance-based and gradient-based models (logistic/linear regression, k-nearest neighbours, SVM, neural nets). Tree-based models do not need it.
- **Transform skew** with logs for money, counts and durations.
- **Create new variables**: ratios, differences, aggregates, date parts, interactions, and above all features suggested by domain knowledge.
- **Flag missingness** where it may carry signal.

## 1.7 Splitting, validation and leakage

A model that looks good on its own training data proves nothing: it may have memorised it.

- **Train / validation / test** (about 60-70 / 15-20 / 15-20%). Use the test set **once**, at the end.
- **Cross-validation** rotates the validation fold for a more stable estimate.
- **Stratify** by class in classification; **split by time** for temporal data; **group** rows from the same customer together.
- **Leakage** is information in training that will not exist at prediction time (a column created after the outcome, scalers fitted on all data, duplicates across splits). Results that seem too good to be true usually are. Wrapping all preprocessing and the model in a **pipeline** fitted on training folds is the best defence.

## 1.8 Models and the bias-variance trade-off

- **Underfitting (high bias)**: too simple; poor on both training and validation data.
- **Overfitting (high variance)**: memorises noise; excellent on training, much worse on validation.

Fixes for overfitting: more data, simpler model, regularisation, fewer features. Fixes for underfitting: better features, a more expressive model, less regularisation. Always start with a **naive baseline** and a **simple model**; complexity must earn its place.

| Model | Strengths | Watch out for |
|---|---|---|
| Linear / Logistic regression (± Ridge, Lasso) | Fast, interpretable, strong baseline | Assumes additive, linear effects; needs scaling; sensitive to extreme values |
| Random forest | Robust, few settings, captures non-linearity and interactions | Larger, slower, harder to explain |
| Gradient boosting | Often the most accurate on tables | More tuning; can chase outliers with squared-error loss |
| k-NN / SVM | Simple (k-NN); good on small, high-dimensional data (SVM) | Need scaling; slow on big data |
| Neural networks | Excel at images, text, audio | Data-hungry, harder to tune and explain |

## 1.9 Evaluation

The right metric reflects the cost of errors. **Accuracy is often misleading.**

- **Regression**: **MAE** (average error in original units, robust), **RMSE** (punishes large errors more), **R²** (share of variance explained). Plot residuals.
- **Classification**: from the confusion matrix (TP, FP, FN, TN): **precision** = TP/(TP+FP), **recall** = TP/(TP+FN), **F1** (their balance), **ROC-AUC** (ranking quality across thresholds), **PR-AUC** (preferred when positives are rare).
- **Thresholds**: classifiers output probabilities; the cut-off that turns them into classes (default 0.5) should be chosen from business cost.
- **Imbalance**: use stratified splits, class weights, PR-AUC and threshold tuning instead of accuracy.

## 1.10 Responsibility and operations

Explain models (coefficients, feature importance, SHAP values). Check performance across subgroups and beware proxy features for protected attributes. After deployment, monitor for *data drift* (inputs change) and *concept drift* (the input-to-target relationship changes), version your data and pipeline, and retrain when performance degrades.

# Part 2: Worked examples

Both examples use deliberately messy synthetic data so that every cleaning step has a visible purpose. All numbers below are the exact output of `worked_example.py` (seed 42). Because the data is simulated, treat the *reasoning* as the lesson, not the specific model ranking, which depends on the data.

## Part 2A: Classification (customer churn)

**Goal:** predict which telecom/subscription customers will churn (cancel) so the retention team can contact them. **Rows:** 15,300 raw (15,000 unique customers). **Churn rate:** 23.2%, so the classes are imbalanced. **Features:** age, tenure, contract type, region, monthly charges, income, support calls, days since last login, signup date.

### Step 0: Inventory the mess (EDA)

Profiling the raw table revealed these problems, each requiring a deliberate decision:

| Problem found | Scale | Treatment | Why this treatment |
|---|---|---|---|
| Exact duplicate rows | 300 rows | `drop_duplicates()` | Duplicates inflate patterns and can sit in both train and test, giving falsely optimistic scores |
| Messy labels (`"MONTH-TO-MONTH "`, `"accra"`) | ~30% of contracts, ~10% of regions | Strip whitespace, title-case | Otherwise one real category splits into several, diluting its signal |
| Impossible ages (-5, 0, 150, 999) | 195 rows | Set to missing | They are entry errors, not information; imputation handles them |
| Placeholder monthly charge `9999` | 164 rows | Set to missing | A sentinel is not a price; left in, it dominates the average and the scaling |
| Missing income (14%) and tenure (3%) | | Median imputation + `income_missing` flag | Median is robust to the skew; the flag keeps the signal if missingness is informative (older customers skip income, a MAR pattern) |
| Heavy-tailed income, ~2% genuine extreme earners | | Keep, but `log1p` and cap at 1st/99th percentile | These are real people, so deleting them would hide real cases; we limit their leverage instead |
| `cancellation_reason` column | | **Dropped** | Only filled in *after* a customer has churned: a leak |
| 23% positive class | | Stratified split, class weights, PR-AUC, threshold tuning | Accuracy would reward predicting "no churn" for everyone |

### Step 1: Prove why leakage matters

Before cleaning anything, we trained a model that still had the `cancellation_reason` column. It scored a **test ROC-AUC of 1.000**. A perfect score on a real-world problem is a red flag, not a victory: the model simply read the answer from a column that does not exist at prediction time. Removing it is the single most important cleaning decision in the example, and it is a *domain-knowledge* decision no algorithm can make for you.

### Step 2: Rule-based cleaning (before the split)

```python
df = df.drop_duplicates()
df["contract"] = df.contract.str.strip().str.title()
df.loc[(df.age < 18) | (df.age > 100), "age"] = np.nan        # impossible -> missing
df.loc[df.monthly_charges > 1000, "monthly_charges"] = np.nan  # sentinel -> missing
df = df.drop(columns=["cancellation_reason"])                  # leakage
```

*Why before splitting?* These are fixed rules, not statistics learned from the data, so they cannot leak information. *Why mark bad values as missing instead of deleting rows?* The rest of the row is still valuable, and imputation later lets us keep it.

### Step 3: Feature engineering (using only what is known at prediction time)

| New feature | Reasoning |
|---|---|
| `income_missing` (0/1) | Missingness may itself predict behaviour |
| `charges_per_tenure` | Captures bill size relative to loyalty |
| `calls_per_year` | Normalises support calls by time as a customer; 4 calls in 3 months is different from 4 calls in 5 years |
| `new_customer` (tenure < 12 months) | Early-life customers churn differently; gives simple models a non-linear threshold |
| `signup_month` | Seasonality of acquisition |
| `log_income` | Compresses the right-skewed, heavy-tailed variable |

### Step 4: Split first, then learn preprocessing inside a pipeline

An 80/20 **stratified** split keeps the churn rate the same in both parts. All learned steps (median imputation, winsorising, scaling, one-hot encoding) sit inside a scikit-learn `Pipeline`, so they are fitted on training data only; during cross-validation they are re-fitted inside every fold. The outlier cap is a small custom transformer that learns its bounds from the training set:

```python
class Winsorizer(BaseEstimator, TransformerMixin):
    def fit(self, X, y=None):
        self.lo_ = np.nanquantile(X, 0.01, axis=0)   # learned from TRAIN only
        self.hi_ = np.nanquantile(X, 0.99, axis=0)
        return self
    def transform(self, X):
        return np.clip(X, self.lo_, self.hi_)
```

*Why scale only for some models?* Logistic regression is sensitive to feature scale, so numeric features are standardised for it. The tree-based models only compare values to thresholds, so scaling changes nothing for them and is skipped.

### Step 5: Compare models, from simplest up

Four models were evaluated with 5-fold stratified cross-validation on the training set and then once on the untouched test set. We report **ROC-AUC** (overall ranking quality) and **PR-AUC** (more informative with 23% positives).

| Model | CV ROC-AUC | CV PR-AUC | Test ROC-AUC | Test PR-AUC |
|---|---|---|---|---|
| Baseline (majority class) | 0.500 | 0.232 | 0.500 | 0.232 |
| Logistic regression | 0.823 | 0.588 | 0.836 | 0.608 |
| Random forest | 0.820 | 0.585 | 0.833 | 0.611 |
| Gradient boosting | 0.823 | 0.590 | 0.838 | 0.621 |

The classification models are built like this (full version in `worked_example.py`, function `run_classification`). Every model shares the same preprocessing, so only the algorithm differs:

```python
from sklearn.dummy import DummyClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier, HistGradientBoostingClassifier
from sklearn.model_selection import StratifiedKFold, cross_val_score
from sklearn.metrics import roc_auc_score, average_precision_score

candidates = {
    "Baseline (majority class)": DummyClassifier(strategy="prior"),
    "Logistic Regression": LogisticRegression(max_iter=2000, class_weight="balanced"),
    "Random Forest": RandomForestClassifier(n_estimators=300, min_samples_leaf=5,
                                            class_weight="balanced_subsample", random_state=0),
    "Gradient Boosting": HistGradientBoostingClassifier(learning_rate=0.05, max_iter=300,
                                                        max_leaf_nodes=15, l2_regularization=1.0,
                                                        random_state=0),
}
cv = StratifiedKFold(5, shuffle=True, random_state=0)
for name, model in candidates.items():
    pipe = Pipeline([("prep", preprocessor), ("model", model)])   # impute -> cap -> scale -> encode
    cv_auc = cross_val_score(pipe, X_train, y_train, cv=cv, scoring="roc_auc").mean()
    pipe.fit(X_train, y_train)
    proba = pipe.predict_proba(X_test)[:, 1]                      # test set touched once
    print(name, cv_auc, roc_auc_score(y_test, proba), average_precision_score(y_test, proba))
```

Notes on the choices: `class_weight` makes errors on the rarer churn class count more; `l2_regularization` and `min_samples_leaf` limit overfitting; the scaler is included in the preprocessor for logistic regression only, since trees do not need it.

**Reading this table honestly:** all three real models beat the baseline decisively, and they are statistically very close. Cross-validated ROC-AUC differs by 0.003, which is within normal noise; the gradient-boosting edge on test PR-AUC (0.621 vs 0.608) is small and not reflected in the cross-validated PR-AUC (0.590 vs 0.588).

### Step 6: Ablation, what did each preparation step actually buy?

To see why each step is needed, we re-trained after adding one step at a time (test ROC-AUC):

| Preparation stage | Logistic regression | Gradient boosting |
|---|---|---|
| Raw data, no cleaning (leak column already dropped) | 0.823 | 0.836 |
| + Cleaning (dedupe, labels, impossible/sentinel values) | 0.833 | 0.839 |
| + Outlier capping (winsorise 1-99%) | 0.833 | 0.838 |
| + Feature engineering | 0.836 | 0.838 |

What this teaches:

1. **Cleaning helped the linear model most (+0.010).** Logistic regression assumes smooth, additive effects, so sentinel values like 9999 and impossible ages distort its coefficients and its scaling. Gradient boosting barely noticed (+0.003) because trees only split on thresholds, so an extreme value is just "greater than the cut-off."
2. **Outlier capping made no measurable difference here**, because the harmful extremes (placeholders, impossible values) had already been removed in cleaning, and the remaining genuine extremes were tamed by the log transform and are not strong drivers. Capping is cheap insurance, not a guaranteed gain. Do not over-claim its value.
3. **Feature engineering helped the simple model (+0.003) and not the flexible one.** Tree ensembles can discover thresholds and interactions (such as "many calls AND short tenure") on their own, while logistic regression needs them handed over as features. This is a general principle: *the simpler the model, the more your features matter.*
4. **Never trust a single comparison to a fraction of a point.** These gains are small and from one split. In practice repeat with several random seeds or repeated cross-validation before drawing conclusions.

### Step 7: Choose the threshold from the business problem

A classifier outputs a probability. At the default threshold of 0.5, gradient boosting catches only 39% of churners. Lowering the threshold trades precision for recall:

| Threshold | Precision | Recall | F1 |
|---|---|---|---|
| 0.50 | 0.68 | 0.39 | 0.49 |
| 0.35 | 0.58 | 0.61 | 0.59 |
| 0.25 | 0.49 | 0.75 | 0.59 |

Always predicting "no churn" would be 76.8% accurate yet catch **0%** of churners, which is exactly why accuracy is the wrong metric here. The right threshold depends on economics: if a retention call is cheap and losing a customer is expensive, choose 0.25 (high recall); if each offer is costly, choose 0.35-0.50.

### Step 8: Which model, and why?

**Recommended: logistic regression as the default; gradient boosting only if the small PR-AUC gain is worth its cost.**

| Criterion | Logistic regression | Random forest | Gradient boosting |
|---|---|---|---|
| Accuracy (CV) | Tied | Tied | Tied (marginally ahead on test PR-AUC) |
| Interpretability | **Coefficients give odds ratios the retention team can read** | Feature importance only | Feature importance / SHAP needed |
| Sensitivity to dirty data | Higher (needs cleaning and scaling) | Low | Low |
| Training and serving cost | **Lowest** | Higher | Moderate |
| Tuning effort | **Minimal** | Low | Higher |
| Handles interactions automatically | No (needs engineered features) | **Yes** | **Yes** |

When accuracy is statistically tied, choose the simpler model: it is easier to explain, audit, monitor and debug. If the business shows that the extra ranking quality translates into real money (say, +0.013 test PR-AUC means a measurably better-targeted campaign), gradient boosting is justified, and it becomes the stronger choice as interactions grow in number and strength.

## Part 2B: Regression (house prices)

**Goal:** predict a property's sale price from size, bedrooms, age, neighbourhood and lot size. **Rows:** 4,000. **Metric context:** prices have a heavy right tail (median about 118,800, maximum about 2.37 million).

### Step 0: Inventory the mess

| Problem found | Treatment | Why |
|---|---|---|
| `sqft` typos (an extra zero, e.g. 1,800 typed as 18,000) and a placeholder value of 15 | 61 rows (<200 or >15,000 sqft) set to missing, then imputed | They are physically implausible data-entry errors, not unusual houses |
| Mixed-case neighbourhood names | Title-case | Prevent category fragmentation |
| Missing `lot_size` (5%) and `age` (3%) | Median imputation | Skew-robust; keeps rows |
| ~1% genuine luxury homes priced 4-9× the norm | **Kept** | Real sales; they exist in the real market. Treated at the *modelling* level rather than deleted |
| Price spread grows with size (errors proportional to price) | Log-transform the target for linear models | Stabilises variance and makes errors proportional |

### Step 1: Feature engineering

`rooms_per_1000sqft` (crowding / layout) and `lot_to_house` (land relative to building) express relationships in ratios that raw columns miss. Neighbourhood is one-hot encoded because it is a nominal category.

### Step 2: Understand the target's outliers before choosing a loss

Luxury homes are a different kind of outlier from the sqft typos. They are **real**, but extreme and not predictable from the available features. They matter in two ways:

- **Squared-error losses and metrics (RMSE, R², mean squared error training) are dominated by them.** One missed luxury home contributes as much as dozens of ordinary mistakes.
- **A raw-price linear model is pulled toward them**, and its errors grow with price (heteroscedasticity).

The remedies are (a) predict `log(price)` so a 9× outlier becomes a modest step, and (b) judge performance with MAE and median percentage error as well as RMSE.

### Step 3: Compare models

Evaluated on a held-out test set, in original currency units:

| Model | MAE | RMSE | R² | Median % error |
|---|---|---|---|---|
| Baseline (mean price) | 68,938 | 119,299 | 0.000 | 39.5 |
| Linear regression, **no cleaning** of sqft errors | 43,148 | 101,925 | 0.270 | 22.4 |
| Random forest, **no cleaning** of sqft errors | 36,584 | 103,777 | 0.243 | 14.8 |
| Linear regression (cleaned, raw target) | 37,253 | 99,562 | 0.303 | 18.4 |
| Linear regression (+ feature winsorising) | 37,115 | 99,470 | 0.305 | 18.4 |
| **Ridge, log target (+ winsorising)** | **32,970** | 100,917 | 0.284 | **14.0** |
| Random forest (cleaned, raw target) | 36,081 | 103,593 | 0.246 | 14.4 |
| Gradient boosting (cleaned, raw target) | 41,231 | 107,409 | 0.189 | 16.9 |
| **Gradient boosting, log target** | 33,152 | 100,746 | 0.287 | **14.0** |

### What the table teaches

1. **Cleaning matters much more to the linear model.** Leaving the sqft typos in raised linear-regression MAE from 37,253 to 43,148 (**16% worse**), while the random forest degraded only from 36,081 to 36,584 (**1.4%**). A 10× typo is a huge leverage point for a straight line, but for a tree it is simply "a very large house," and it lands in the same branch as other large houses. Robustness to bad data is a genuine advantage of trees, but it does not excuse leaving bad data in.
2. **The target transform was the most effective outlier treatment.** Switching to a log target improved gradient boosting's MAE from 41,231 to 33,152 (**20% better**) and the linear model's from 37,115 to 32,970. Gradient boosting with the default squared-error loss chases luxury homes, which spoils its fit for the typical house. Logging the price removes that pull.
3. **Capping *features* at the 1st/99th percentile changed almost nothing** (37,253 to 37,115 MAE), because the damaging feature outliers were already fixed by the rule-based sqft cleaning.
4. **RMSE and R² barely distinguish the models, and R² is modest (about 0.3 for all).** This is because about 1% of homes have an unpredictable 4-9× price multiplier whose squared errors swamp everything else. This is not a model failure but a metric choice: **MAE and median percentage error describe the typical buyer's experience far better here.** A model that is typically within 14% of the true price is useful even though R² looks low. Report several metrics and say which one matches the decision.
5. **Caution on the log target:** predictions are back-transformed with `expm1`, which tends toward the *median* price rather than the mean. That is appropriate for typical-case estimates, but if you need total portfolio value, check for systematic under-prediction and consider a bias correction.

### Which model, and why?

**Recommended: Ridge regression on a log-transformed target.**

- It is **statistically tied** with gradient boosting on the log target (MAE 32,970 vs 33,152; median error 14.0% for both).
- With a log target, each coefficient reads as an approximate **percentage change in price** ("each extra 100 sqft adds about x%"), which agents and buyers can understand and challenge.
- It trains in milliseconds, has little to tune and is easy to monitor.
- Choose gradient boosting if more data, more features (location coordinates, amenities) or stronger interactions appear, since that is where it pulls ahead of linear models.
- **Avoid** the raw-target gradient boosting configuration: it was the worst flexible model, an example of a powerful model being undermined by an unexamined target distribution.

# Outlier treatment: a decision guide

| Question | If yes | Technique | Notes |
|---|---|---|---|
| Is it impossible or a clear entry error? | Fix or set to missing | Rule-based cleaning (domain limits) | Safe before splitting; never use learned statistics to *define* an error |
| Is it a genuine extreme in a **feature**, and the model is linear, distance-based or neural? | Limit leverage | Log or Box-Cox transform; winsorise at percentiles learned from train | Cheap insurance; gains may be small |
| Same, but the model is tree-based? | Usually do nothing | None needed | Trees only use order, not magnitude |
| Genuine extremes in the **target** (regression)? | Reduce their pull | Log-transform the target; robust loss (Huber, quantile / MAE); report MAE and median error | Biggest effect in our regression example |
| Are the extremes the cases you care most about (fraud, rare disease)? | **Keep them** | Use stratification, class weights, recall-focused metrics | Removing them removes the thing you want to detect |
| Unsure whether it is an error or real? | Investigate | Ask a domain expert, check the data source | Do not delete merely because it hurts the fit |

Detection tools: visual inspection (box plots, scatter plots), the IQR rule (values beyond 1.5 × IQR from the quartiles), z-scores, and plain domain sense ("can a house have 15 sqft?"). Record every decision and how many rows it affected, as the cleaning log in the script does.

# Choosing between models

| Situation | Reasonable first choice | Why |
|---|---|---|
| You need to explain every prediction (credit, healthcare, HR) | Logistic / linear regression (regularised) | Transparent coefficients; easy to audit |
| Tabular data, many interactions, accuracy matters most | Gradient boosting | Strong default on tables; handles non-linearity and mixed types |
| Messy data with many outliers and little time to prepare | Random forest | Robust, few settings, hard to ruin |
| Small data set | Regularised linear model, small tree ensembles | Flexible models overfit |
| Images, text, audio | Neural networks | Learn representations from raw data |
| Performance is tied | **The simpler model** | Cheaper, more stable, easier to maintain |

A dependable procedure: build the naive baseline, then a regularised linear model, then a random forest and gradient boosting, compare with the *same* cross-validation, and choose the simplest model whose performance is within noise of the best.

# Pitfalls checklist and next steps

**Pitfalls**

- Starting from the algorithm instead of the decision
- Skipping EDA and trusting the data
- Fitting imputers, scalers or outlier caps on all data before splitting
- Leaving in a feature that is only known after the outcome
- Using accuracy on imbalanced classes
- Reusing the test set to make choices
- Random splits on time-ordered data
- Deleting outliers to improve the score
- Declaring a winner on a 0.003 difference from a single split
- Ignoring how the model will be monitored and retrained

**Next steps**

- Re-run `worked_example.py` with different seeds and observe how stable the rankings are
- Replace the synthetic generators with a real dataset (Kaggle, UCI Machine Learning Repository) and repeat the same inventory, cleaning log, ablation and metric reasoning
- Try Lasso for feature selection, quantile or Huber regression for outlier-robust targets, and SHAP for interpreting the boosted models
- Further reading: *An Introduction to Statistical Learning* (James, Witten, Hastie, Tibshirani; free online), *Hands-On Machine Learning with Scikit-Learn* (Aurélien Géron), and the scikit-learn user guide

> **Rule of thumb to remember:** clarify the decision, respect the data, protect the test set, begin simple, and let the cost of errors, not habit, choose your metric and model.
